# 成立条件复核：简化协议在本批开发材料中表现更好

新协议在本批六例中保留了三个正确稿，定位了两个错误结论，并将缺少定理的陈述标为需要来源。没有结构失败。完整 v2 出现三次格式或引用拒绝，以及一例“误报正确句、放过错误句”的语义问题。结果支持继续试验简化方向，尚不足以启用默认自动复核。

## 逐句观察

| 案例 | 完整 v2 | focused |
| --- | --- | --- |
| 归一化正确稿（已见回归） | 非法 JSON 被拒绝 | 保留三个单元 |
| 归一化错误稿（已见回归） | 错误结论被保留，正确公式被要求补条件 | 保留公式，指出负缩放会反向 |
| 对数定义域错误稿 | 看出错误，但把笔记当作来源引用，被拒绝 | 以 x=y=-1 反驳，引用来源正确 |
| 对数正确稿 | 保留 | 保留，无重复条件或推导要求 |
| 缺定理原文 | 看出缺口，但 missing 字段类型错误，被拒绝 | 需要来源，不当作已证伪 |
| 谨慎的实验表述 | 保留 | 保留 |

开发标签一致项为 v2 的 3/6、focused 的 6/6，**不能作为准确率**。尤其 v2 在归一化错误稿上的 issue 标签来自错误位置：p1:s1 正确公式被 qualify，p1:s2 错误结论反而 preserve。标签碰巧一致掩盖了误报与漏检同时发生。[逐条证据](findings.json) 和回归测试明确保留这一差别。

对数错误稿和缺定理案例中，v2 的原始语义已经看出问题，失败发生在引用或字段类型；不能把三次结构失败全部描述为推理失败。focused 本批没有使用 missing-condition 分支，也没有生成修改，因而未验证该分支的真实语义表现或修订质量。

两例是已见失败，四例为与协议一起设计的开发稿；每例每组仅运行一次。标签和本文判断由 AI 协作完成，尚未经过独立人工复核。下一轮应把协议固定，转向真实笔记片段和独立审阅，而不是在这六例上继续调参。

## 复现与证据

[run.json](run.json) 保留原始请求、响应、失败、诊断、代码版本及预算。[findings.json](findings.json) 绑定运行哈希，每条观察引用实际字段；坏 JSON 引用原始字符串，不先修好再算成功。

```sh
npm run eval:claims -- --inspect evals/claims/runs/2026-10-18-focused/run.json --out artifacts/claim-eval/2026-10-18-focused-replay
```

重放不读取 Key，也不请求模型。两组并排展示，所有原稿保留；引用和范围通过不代表语义已认证。
