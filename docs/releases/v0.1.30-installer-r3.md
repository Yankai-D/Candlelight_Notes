# 0.1.30 · Windows installer revision 3

r2 修改了新安装器的进程检测，但覆盖升级仍会调用安装目录中的旧卸载器；旧检测逻辑可能重新生效，而且上游把多种旧卸载器失败统一显示为“应用无法关闭”。r3 在用户确认安装之后调用随当前安装包构建的卸载组件，保留 `--updated` 数据策略，再安装新版本。不会预先改写用户安装目录中的卸载器。

r2 corrected the new installer's process check, but upgrades still invoked the installed legacy uninstaller. That could reintroduce the old checks, while upstream reported several different uninstall failures as an application-close error. After the user confirms installation, r3 invokes the current bundled uninstall component with the existing `--updated` retention policy, then installs the new version. It does not patch the user's installed uninstaller beforehand.

文件替换失败时保留实际失败路径，执行原有移动／恢复事务，并停止写入新版本。诊断记录保存在安装器缓存旁的 `installer.exe.log`，限制约 64 KiB，只记录升级阶段和错误路径。不会记录 Key、画像或笔记正文。正常卸载继续删除 Key，外部资料和笔记保留。

File replacement failures retain the actual failing path, run the existing move/restore transaction, and stop before writing the new version. A bounded log of roughly 64 KiB, `installer.exe.log`, resides beside the installer cache and records upgrade stages and failing paths only. It does not record keys, profiles, or note contents. Normal uninstall still removes credentials and retains external materials and notes.

完整事务回归由 `npm run test:installer:upgrade -- <win-unpacked>` 执行。测试使用真实应用主体、独立 appId／GUID／画像／缓存，禁用快捷方式和自动启动，验证六个场景：首次安装；故意损坏旧卸载器后的覆盖升级；真实文件占用后的错误定位和全部文件哈希回滚；释放占用后的重复安装；安装目录内启动安装包的转交升级；卸载清除 Key 且保留资料。另有 10 项原生进程／转交检查和既有目录、卸载策略与桌面测试。

`npm run test:installer:upgrade -- <win-unpacked>` runs complete transactions with the real application payload and isolated app ID, GUID, profile, and cache; shortcuts and automatic launch are disabled. Six scenarios cover fresh installation, upgrade with a deliberately failing legacy uninstaller, real file-lock diagnosis and byte-for-byte rollback, reinstall after releasing the lock, handoff from Setup inside the install directory, and credential removal with external data retention on uninstall. Ten native process/handoff checks and the existing directory, uninstall-policy, and desktop tests provide additional coverage.

普通旧版→r2 升级和目录内启动 r2 在隔离环境中均成功，因此没有直接复现用户机器上的原始触发条件。故障注入验证了旧卸载器失败和真实文件锁两类问题；没有操作个人安装版，也没有自动测试原生向导的视觉外观。应用主体仍为已验收的 0.1.30，本次仅更新安装器。安装包未签名，未发布到 GitHub。

Ordinary legacy-to-r2 upgrades and r2 handoff both succeeded in isolation, so the original machine-specific trigger was not directly reproduced. Fault injection verified legacy-uninstaller failures and real file locks. The personal installation was not modified, and the native wizard's visual appearance was not automated. The application payload remains the previously validated 0.1.30; this revision changes the installer only. The installer is unsigned and has not been published to GitHub.

文件移动和恢复事务沿用 electron-builder 的 NSIS 模板（MIT），具体来源在 `packaging/desktop/installer-upgrade.nsh` 中标注；依赖及许可记录见项目致谢和随包第三方声明。

The move/restore transaction derives from electron-builder's MIT-licensed NSIS template, attributed in `packaging/desktop/installer-upgrade.nsh`; dependency and license records remain in the project acknowledgements and bundled third-party notices.
